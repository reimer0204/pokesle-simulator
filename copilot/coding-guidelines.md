# コーディングルール・設計方針

この文書は、現在のコードベースから読み取れる慣習と設計上の判断をまとめたものです。新規実装や修正では、依頼内容や既存仕様と矛盾しない範囲で本方針に従ってください。

## 1. プロジェクトの前提

- Vue 3、Vite、Vue Router、TypeScript/JavaScript、SCSSを使用するクライアントサイドアプリです。
- サーバーレスで、シミュレーションやデータ処理は利用者のブラウザ内で完結させます。
- 画面遷移には `createWebHashHistory()` を使い、GitHub Pages向けの静的成果物を `docs/` に出力します。
- 開発は `npm run dev`、本番ビルドは `npm run build` を基本とします。
- `docs/`、`components.d.ts`、`auto-imports.d.ts`、`src/auto-imports.d.ts` などの生成物は、必要な生成処理の結果でない限り手編集しません。

## 2. ディレクトリと責務

- `src/pages/`: ルート単位の画面と、画面固有の状態・オーケストレーションを置きます。
- `src/components/`: 複数画面で再利用するUI、フォーム、表示部品、ポップアップを置きます。
- `src/models/`: 設定、永続化、シミュレーション、Worker制御などのドメインロジックを置きます。
- `src/data/`: ポケモン、食材、料理、スキルなどのマスターデータと、その派生情報を置きます。
- `src/worker/` および `?worker` で読み込むファイル: CPU負荷の高い処理を置きます。
- `src/type.ts`: 複数領域で共有する主要なドメイン型を置きます。
- 画面コンポーネントを肥大化させず、再利用可能なUIは `components`、計算や状態管理は `models` へ寄せます。
- 基準生成と簡易診断で共有する厳選設定は `components/evaluate-setting.vue` に集約し、設定先だけをpropsで切り替えます。簡易診断専用の基準値は同コンポーネントの末尾スロットへ追加します。

## 3. Vueコンポーネント

- Composition APIと `<script setup>` を基本とします。
- Vueの `ref`、`reactive`、`computed`、`watch`、ライフサイクルAPIは自動インポート設定を利用できます。既存ファイルの流儀に合わせ、不要な明示インポートを増やしません。
- コンポーネントの入力と出力は `defineProps` / `defineEmits` で明示します。
- 派生値はテンプレート内へ複雑な式を重ねず、`computed` に切り出します。
- 副作用や非同期処理は関数として命名し、画面の初期化・イベント・監視から呼び出します。
- 親子ルートを持つ画面は、親で共有状態を準備し、`router-view` のpropsで子へ渡す既存パターンを優先します。
- コンポーネントのファイル名は既存どおりkebab-case、インポートしたコンポーネント名とクラス名はPascalCase、変数・関数はcamelCaseを使います。

## 4. UIとスタイル

- UIを追加・変更する前に `src/pages/design-system.vue` を確認し、目的に合うデザインシステム部品を優先して使用します。該当部品がない場合のみ、既存画面に調和するUIを実装します。
- 新しいUIを独自実装する前に、`DesignTable`、`SortableTable`、`SettingList`、`TabList`、`InputText`、`InputNumber`、`InputPassword`、`InputFile`、`InputSelect`、`InputRadio`、`InputCheckbox`、`FormButton`、`ToggleArea` など既存部品を再利用します。
- クリックでポップアップを開いて選択値を決めるUIは、右側に矢印を表示する `SettingButton` をトリガーとして使用します。選択ポップアップを `Popup.show(...)` で開く場合も、`SettingButton` の `@click` から起動します。
- 設定画面内のカテゴリ、個別ルール、入力項目の見出しには、役割に応じて `SettingSectionTitle` の `category`、`item`、`field` を使用します。
- 関連する複数の設定を見出し付きの枠で区切る場合は、`SettingGroup` を使用します。グループ単位の操作は、`actions` スロットでヘッダー右端に配置します。
- 画面内で中心となる実行操作には、`FormButton` の `execute` クラスを使い、青色で通常のブルーグレーの操作から区別します。削除などの重要・破壊的な操作には従来どおり `important` を使います。
- 画面と共通表示コンポーネントでは、ネイティブな `input`、`select`、`button` を直接配置せず、`components/form/` の対応コンポーネントを使います。ネイティブ要素はフォームコンポーネントの実装内部に限定します。
- `InputText`、`InputNumber`、`InputSelect` の編集値は原則として `v-model` で渡します。空欄時の `null` や `0` への変換など個別の正規化が必要な場合は、`model-value` と `@update:model-value` を対にして扱います。
- 一覧は `SortableTable` の `columnList` と名前付きスロットを使い、ソート・固定列・数値表示の挙動を統一します。
- ポップアップは原則として `Popup.show(Component, props)` を使い、結果が必要なら返されるPromiseを `await` します。
- UI文言とドメインコメントは、既存画面に合わせて日本語を基本とします。
- コンポーネント固有のスタイルは `<style lang="scss" scoped>` に置きます。
- レイアウトや余白は `src/bootstrap.scss` のflex、幅、高さ、margin、padding、gap等のユーティリティを優先し、再利用できない見た目だけをscoped SCSSへ追加します。
- 色は `src/style.scss` のCSS変数を優先し、広い面積には低彩度のブルーグレーとニュートラルな背景色を使います。主要操作はブルーグレー、補助的な選択状態はミント、重要操作・エラーはDanger、注意はオレンジを使い、鮮やかな色は状態を伝える範囲に留めます。表はセル余白をむやみに増やさず、背景色・罫線・ホバーで状態を伝えます。
- レスポンシブ対応で表や一覧の構造を切り替える場合も、`DesignTable`、`SortableTable` 等の共通部品と同じトークン・余白・角丸を使い、画面幅によって見た目のデザインシステムを分断しません。
- 画面全体は高さ制約と `min-height: 0`、flex、必要箇所のoverflowを意識し、既存のデスクトップ表示を崩さないようにします。
- 画面は幅390px程度のスマートフォンでも操作できるようにします。ページ全体を横にはみ出させず、列数の多い表や入力グリッドなど横幅が必要な要素だけを内部スクロールさせます。
- 幅600px以下の縦画面、または高さ500px以下・幅900px以下の横画面では、共通ヘッダーとタブを1行の横スクロール、固定列グリッドを縦積み、左右分割を上下分割へ切り替える既存のモバイル方針を維持します。
- モバイルの`main`は、固有のスクロール領域を持たない通常ページの縦スクロールを受け持ちます。表や結果など高さを固定する画面では、必要に応じてページ内の専用スクロール領域を維持します。
- ポップアップはモバイルでビューポート内に収め、ヘッダーと閉じる操作を見失わず、本文だけをスクロールできる構造を優先します。
- レスポンシブ対応時は、デスクトップの情報量を無理に削除せず、文字・余白の縮小、折り返し、内部スクロールで機能へ到達できることを優先します。

## 5. 状態管理と永続化

- 全体設定は `src/models/config.ts` のリアクティブな `config` を正とし、設定項目の初期値は `src/data/default-config.ts` に追加します。
- 設定更新時は既存設定を丸ごと置き換えず、`mergeObject` とデフォルト値を利用して旧バージョンの保存データとの互換性を保ちます。
- 保存形式を変える移行は `config.v` を基準に、localStorage読込直後・`mergeObject` の前で一度だけ実行し、完了後に現行バージョンへ更新します。
- 編集画面で確定前の値が必要な場合は `config.clone()` で作業用コピーを作り、確定時に `config.save()` します。
- 画面固有の小さな永続データにlocalStorageを使う場合は、用途が分かる固有キーを定数化します。
- localStorageの読み込みとJSON解析は `try/catch` で保護し、欠損値・旧形式・不正値では安全な初期値へ戻します。
- マスターデータを画面上で編集する場合は、`structuredClone` 等でコピーしてからリアクティブ化し、`Cooking.list` や `Pokemon.list` などの共有マスターを直接変更しません。

## 6. データとドメインモデル

- マスターデータは、既存の `static list` と `static map` の構成を踏襲します。列挙は `list`、名前からの参照は `map` を使います。
- 画面や計算処理で文字列リテラルの集合を扱う場合は、可能なら `src/type.ts` のunion型や共有interfaceを利用します。
- ポケモン・食材・スキル等の関連付けや派生値は、各画面で重複計算せず、データ初期化またはモデル層へ集約します。
- エネルギー、確率、重み、パーセンタイルなどの計算ロジックを変更する場合は、丸め位置、単位、重み付け、境界値を維持しているか確認します。
- ドメイン上の理由がコードだけでは分かりにくい処理には、「何をしているか」より「なぜ必要か」が分かる日本語コメントを付けます。

## 7. 非同期処理とWeb Worker

- 画面を長時間ブロックする組み合わせ探索やシミュレーションはWeb Workerへ置き、UIスレッドでは実行しません。
- Workerの並列実行は `MultiWorker` を利用し、基本プロトコルとして `{ status: 'progress' | 'success' | 'error', body }` を維持します。
- Worker数は原則として `config.workerNum` を尊重し、逐次実行が必要な処理のみ明示的に1を指定します。
- 進捗を表示する非同期処理は `asyncWatcher.run(...)` と `ProgressCounter` を利用します。
- コンポーネント内で生成したWorkerは、処理完了時または `onBeforeUnmount` で必ず `close()` し、Workerを残しません。
- Workerへ渡す値は構造化複製可能なプレーンデータにし、リアクティブProxyや関数を直接渡しません。必要に応じて設定をJSONで複製します。
- 多重ループ内では、不変値の事前計算、Map化、配列生成の削減を優先し、結果の意味を変えずに負荷を抑えます。

## 8. JavaScript / TypeScriptの書き方

- `.js` と `.ts` が共存する段階的なTypeScript化のプロジェクトです。新規の複雑なモデルや型安全性が重要な処理はTypeScriptを優先しますが、既存ファイルを理由なく全面変換しません。
- 共有型は再利用し、同じ構造の大きな型定義を画面ごとに複製しません。
- importは同一領域では相対パス、離れた領域や共通資源では `@/` エイリアスが使われています。変更先の既存スタイルに合わせます。
- セミコロン、引用符、`const` / `let` などには既存コード上の揺れがあります。大規模な整形を行わず、変更箇所周辺のスタイルを維持します。
- 可読性のため、式・props・属性・子要素・SCSS宣言を1行に詰め込みすぎません。行が長くなる場合は意味のまとまりごとに改行し、インデントを揃えます。
- `()`、`[]`、`{}`、`<>` などの対応する記号を複数行に分ける場合、閉じ記号の行は開き記号がある行と同じインデントにします。関数呼び出し・配列・オブジェクト・ジェネリクス・Vueタグでこの規則を統一します。
- Vueタグを複数行で書く場合は、開始タグのタグ名を単独行にし、属性は次行以降に置きます。開始タグを閉じる `>` または `/>` はタグ名と同じインデントにそろえます。
- Prettier（`printWidth: 100`）で整形します。通常は `npm run format:file -- <変更ファイル>` を使い、依頼と無関係な既存ファイルを一括整形して差分を増やさないよう注意します。全体整形は `npm run format`、CI等の確認は `npm run format:check` を利用できます。
- 比較、nullの扱い、配列操作についても、機能変更と無関係な一括置換は避けます。
- 変更範囲外の命名、整形、リファクタリングを混ぜず、差分を依頼内容へ限定します。

## 9. エラー処理と互換性

- 保存データ、IndexedDB、外部取得、Workerなど失敗し得る境界では例外を考慮します。
- 復旧可能な保存・読み込みエラーは安全な既定値へフォールバックし、計算不能や未実装など結果の信頼性に関わるエラーは握り潰しません。
- 設定や永続データの形式を変える場合は、既存ユーザーのデータを失わない移行または後方互換処理を用意します。
- 新機能は既存ルート、既存一覧、既存ポップアップの操作を壊さない形で追加します。

## 10. 変更時の確認

- 最低限、変更ファイルの構文、関連画面の表示、主要操作、ブラウザコンソールエラーを確認します。
- 実行環境が揃っている場合は `npm run build` を実行します。型確認コマンドが利用可能なら併せて実行します。
- ローカル画面の変更では、対象URLを実ブラウザで開き、入力、タブ切替、画面更新、スクロール等の変更に関係する操作を確認します。
- 永続化の確認では、値を変更して再読み込み後に復元されることを確認し、テスト用に変更した利用者データは元へ戻します。
- パフォーマンス修正では、出力が従来と等価であることを優先し、可能なら処理件数・割り当て・ソート回数など改善根拠も確認します。
- `git diff --check` で不要な空白エラーがないことを確認し、ユーザーの既存変更や生成物を勝手に戻しません。

## OCR

- スクリーンショットOCRは `src/models/ocr/` の専用クラスとして実装し、画面ごとのレイアウトをまたぐ曖昧な推定を避けます。
- 読み取り対象の表示要素に位置関係がある場合は、OCR文字列だけでなくバウンディングボックスも使い、期待される相対位置にある値だけを対応付けます。
- 食材バッグでは、食材名を先にマスターデータへ照合し、その直上かつアイコン右下に相当する範囲の `x<数字>` だけを個数として採用します。
- TesseractのWorker・Core・日本語学習データは `public/ocr/` の同梱ファイルを使い、スクリーンショットを外部サービスへ送信しません。
